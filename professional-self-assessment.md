## Technical Skills and Problem-Solving

My Java programming and software-testing skills improved the most during the program. Earlier in my education, I was often focused on getting code to work. As I gained experience, I started paying more attention to how the code was organized, how another person might understand it, and how I could prove that it worked under different conditions.

CS 320 was one course that made a noticeable difference in my development. In that course, I built contact, task, and appointment services in Java and used JUnit to test whether each one met its requirements. That experience changed how I approached programming because I began thinking about how I would verify my code while I was still writing it. It also gave me more confidence with Java and made the testing work in this capstone feel much more familiar.

The most challenging part of the capstone was refactoring the original application. Its basic features worked, but too many responsibilities were concentrated in a small number of Activity classes. Improving the structure required more than adding new features. I had to determine which responsibilities belonged together, separate them into appropriate classes, and preserve the application’s original behavior while making it easier to maintain. Classes for validation, inventory records, inventory display, account registration, SMS behavior, and inventory organization gave the application a clearer structure. Refactoring was challenging because a structural change can affect several parts of an application even when the visible behavior is supposed to remain the same. Automated tests helped me make those changes with greater confidence.

Software design and engineering is the area that best represents my abilities. I enjoy visualizing how I want an application to work and then turning that idea into a functioning design. The completed application reflects my ability to take a working but limited project, identify weaknesses, and improve its organization and usability. This process also showed me how much my programming proficiency has grown. When I returned to the original CS 360 application, I could see places where my earlier work felt rushed or loosely organized. Code that would have been difficult for me to change before was easier to understand and improve because I now approach problems more methodically.

The algorithms and data structures enhancement strengthened my ability to select tools according to the problem being solved. The application uses a list for its primary inventory collection, a HashMap for efficient exact-SKU lookup, and a PriorityQueue for restocking needs. This work taught me that one structure is not automatically the best choice for every operation. Exact lookup, partial searching, sorting, and priority ordering have different requirements. I also had to consider the trade-off created by storing related information in multiple structures. Rebuilding the supporting structures after an inventory change requires additional processing, but it reduces the chance of stale or inconsistent data. That decision was appropriate for the expected size and purpose of this application.

Testing became an important part of evaluating these decisions. The completed project includes 18 local unit tests covering validation and inventory organization. It also includes 11 Android instrumented tests covering database and SMS behavior. These tests check normal operations as well as duplicate records, invalid quantities, overflow, unauthorized access, migration, persistence, and transaction rollback. Developing this evidence changed how I think about software quality. A feature is more convincing when its behavior can be repeated and verified instead of being supported only by a successful demonstration.

## Collaboration and Communication

The capstone itself was an individual project, so my strongest evidence of collaboration comes from how I worked with instructor feedback and prepared the project for review by others. My professor asked for stronger verification of migration, account ownership, and persistence. I responded by adding focused Android instrumented tests and organizing the screenshots and generated reports so another reviewer could connect each claim to a result. That process showed me that useful feedback can expose gaps I may not recognize while working alone.

This experience taught me that collaboration includes listening carefully, understanding the reason behind feedback, and converting that feedback into useful technical decisions. In a team environment, I would use the same approach when working with developers, managers, users, or other stakeholders. I also structured the code so that it could be understood and maintained by a team. Responsibilities are divided among focused classes, names communicate their purpose, and comments explain decisions that may not be obvious from the code alone. Automated tests give another developer a way to confirm existing behavior before making changes. The code-review video, narratives, screenshots, generated reports, and ePortfolio communicate the work at different levels of detail. A technical reader can inspect the source code and test reports, while a less technical stakeholder can use the narratives and portfolio summaries to understand the purpose and value of each enhancement. These practices support collaboration and decision-making even though the implementation was completed independently.

## Databases and Security

The database enhancement expanded my understanding of how software design and security are connected. The original application stored passwords as readable text and treated inventory as a shared collection. The enhanced application uses salted password hashing, parameterized queries, account-owned inventory, ownership checks, constraints, transactions, and versioned migrations. Inventory history is also restricted to the signed-in user. These changes demonstrate a security mindset because they anticipate what could happen if someone entered unexpected input, attempted to access another account’s records, or caused one part of a database operation to fail.

Input validation is applied before data reaches important application and database operations, while database constraints provide another layer of protection. Transactions keep an inventory change and its history record consistent. Migration logic preserves earlier data while removing plaintext passwords and introducing account ownership. This work taught me that security should be considered during design instead of being added after the rest of the application is finished. Privacy, data integrity, authentication, and error handling all influence how classes, queries, and database tables should be designed.
